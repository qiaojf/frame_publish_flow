# X / Instagram / YouTube / Facebook 发布平台接入指南

> 查阅日期：2026-09-11  
> 适用项目：本仓库的视频制作发布平台  
> 文档用途：申请官方应用、准备 OAuth 配置、收集账号资料，以及后续实现真实发布 Adapter 的参考清单。  
> 信息来源：仅使用 X、Meta、Google/YouTube 的官方开发文档和 Meta 官方 Postman 工作区。平台权限、配额、审核规则和 API 版本会调整；真正上线前，应以各控制台当时显示的要求为准。

## 1. 先看结论

| 平台 | 推荐认证方式 | 实际发布目标 | 最小发布权限 / Scope | 关键前置条件 |
| --- | --- | --- | --- | --- |
| X | OAuth 2.0 Authorization Code + PKCE | 授权用户的 X 账号 | `tweet.read`、`users.read`、`tweet.write`、`media.write`、`offline.access` | X Developer 账号、Project/App、可用额度 |
| Instagram | **Instagram API with Instagram Login** | Instagram 专业账号 | `instagram_business_basic`、`instagram_business_content_publish` | Business 或 Creator 账号；媒体需能被 Meta 公网访问 |
| YouTube | 服务端 OAuth 2.0，申请 offline access | 授权用户选定的 YouTube Channel | `https://www.googleapis.com/auth/youtube.upload` | Google Cloud Project、启用 YouTube Data API v3、频道 |
| Facebook | Facebook Login + Page Access Token | Facebook Page，不是个人主页 | `pages_show_list`、`pages_read_engagement`、`pages_manage_posts` | Facebook Page、用户对 Page 有创建内容权限、Meta App |

建议优先采用 Instagram Login 路线。它不要求 Instagram 专业账号绑定 Facebook Page，且与本项目预置的 `https://graph.instagram.com` 基础地址一致。只有在需要复用 Facebook Page、统一 Meta 授权或使用该路线特有能力时，才选择 Instagram API with Facebook Login。两条路线的 Host、Token 类型、Scope 和账号 ID 不同，不能混用。

## 2. 四个平台共用的准备工作

### 2.1 公网服务信息

正式接入前需要准备：

- 一个由你控制的 HTTPS 域名，例如 `https://publish.example.com`。
- 每个平台独立、固定且精确匹配的 OAuth 回调地址。建议规划为：
  - `https://publish.example.com/api/v1/oauth/x/callback`
  - `https://publish.example.com/api/v1/oauth/instagram/callback`
  - `https://publish.example.com/api/v1/oauth/youtube/callback`
  - `https://publish.example.com/api/v1/oauth/facebook/callback`
- 隐私政策 URL、服务条款 URL、用户数据删除说明或回调 URL、支持邮箱。
- Instagram 发布使用的公网媒体域名或对象存储/CDN。Meta 会从 `video_url`/`image_url` 主动拉取文件，所以 `localhost`、内网地址、需要浏览器 Cookie 的地址均不可用。
- 本项目已提供无需登录的 `GET/HEAD /videos-pub/{video_id}`。本地可用 `http://localhost:5173/videos-pub/{video_id}` 验证；交给平台的 `video_url` 必须换成公网 HTTPS 域名，例如 `https://publish.example.com/videos-pub/{video_id}`。
- OAuth 回调和媒体地址应区分开发、测试、生产环境。不要让生产 App 回调到开发机器。

上述路径只是本项目的**建议规划**，不是现有接口；实现 OAuth 时仍需在后端增加对应路由。

### 2.2 安全与数据要求

- `client_secret`、Access Token、Refresh Token 只进入后端，并使用项目现有加密字段保存；不要放进前端、本 Markdown、Git、日志或 Celery 异常文本。
- OAuth 请求必须使用一次性 `state` 防 CSRF；X 还必须正确校验 PKCE `code_verifier`。
- 保存实际授权 Scope、Token 到期时间、授权账号的官方 ID。不要仅保存用户名，因为用户名可以变更。
- 刷新 Token 时使用数据库锁或分布式锁，避免多个 Celery Worker 同时刷新并互相覆盖。
- 平台返回的 Post/Media/Video ID、公开 URL、请求追踪 ID 和处理状态应写回发布任务，供幂等、重试和审计使用。
- 发布重试必须先查询上一次上传/发布状态，不能收到超时就直接重复发帖。
- API 版本应显式固定在平台配置中，并建立升级检查流程；不要长期依赖 Meta 的隐式默认版本。

### 2.3 审核材料

面向非开发者/非测试员账号开放时，通常需要准备：

- 应用名称、Logo、主页、隐私政策、服务条款和支持邮箱。
- 每个权限为什么必需、在产品哪个页面触发、数据如何使用和删除。
- 从登录、授权、选择账号、上传、发布到查看结果的完整录屏。
- 审核人员可以使用的测试账号、操作步骤和可访问环境。
- 域名所有权、企业主体/Business Portfolio 等控制台要求的证明。

测试阶段只连接你自己管理、并已加入应用角色/测试名单的账号，可以先完成技术验证；外部用户接入则按控制台要求申请 Advanced Access、OAuth Verification 或平台审核。

## 3. X 接入

### 3.1 账号和应用前置条件

1. 使用 X 账号进入 [X Developer Console](https://console.x.com/)，接受 Developer Agreement，并填写真实 API 用途。
2. 创建 Project/App，记录 App 名称和用途。
3. 在 App Authentication Settings 中启用 OAuth 2.0，应用类型选择适合服务端 Web 应用的 confidential client。
4. 配置 Website URL、生产回调 URL；如控制台要求，再配置隐私政策和服务条款。
5. 检查 Developer Console 中的用量/付费状态。X 当前文档将 API 描述为按使用量计费，实际可用端点和额度以控制台为准。

官方入门文档说明，代用户发帖需要已批准的开发者账号、Project/App 和 User Access Token；App-only Bearer Token 适合只读公共数据，不能替代用户授权来发帖。参见 [Getting Access](https://docs.x.com/x-api/getting-started/getting-access)、[Manage Posts](https://docs.x.com/x-api/posts/manage-tweets/introduction) 和 [Developer Console](https://docs.x.com/fundamentals/developer-portal)。

### 3.2 OAuth 配置

建议请求以下最小 Scope：

| Scope | 用途 |
| --- | --- |
| `tweet.read` | 读取授权流程和发帖相关的基础 Post 数据 |
| `users.read` | 获取并确认授权用户身份 |
| `tweet.write` | 创建 Post |
| `media.write` | 上传图片/视频/GIF |
| `offline.access` | 获得 Refresh Token，以支持定时发布和后台刷新 |

接入流程：

1. 后端生成高熵 `state`、`code_verifier` 和 S256 `code_challenge`，并将短期状态绑定到当前平台用户。
2. 将用户重定向到 `https://x.com/i/oauth2/authorize`，携带 `response_type=code`、`client_id`、精确匹配的 `redirect_uri`、Scope、`state`、`code_challenge` 和 `code_challenge_method=S256`。
3. 回调时先验证 `state`，再用授权码与原 `code_verifier` 请求 `POST https://api.x.com/2/oauth2/token`。
4. 加密保存 Access Token、Refresh Token、到期时间和实际授权 Scope。
5. Access Token 将到期时，用同一 Token 端点和 `grant_type=refresh_token` 刷新。只有请求 `offline.access` 才会发放 Refresh Token。

官方要求回调 URL 与控制台登记值精确一致；生产使用 HTTPS，本地开发使用 `http://127.0.0.1` 而非 `localhost`。详见 [X Apps 与回调 URL](https://docs.x.com/fundamentals/developer-apps) 和 [OAuth 2.0 PKCE](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code)。

### 3.3 视频发布调用顺序

1. 校验媒体类型、大小、时长和编码；视频使用 `media_category=tweet_video`。
2. 使用 X 官方 Chunked Media Upload：`INIT` → 多次 `APPEND` → `FINALIZE`。
3. 如果 `FINALIZE` 返回 `processing_info`，按照 `check_after_secs` 查询 `STATUS`，直到 `succeeded` 或 `failed`。
4. 记录 `media_id`；媒体 ID 有有效期，应尽快创建 Post。
5. 请求 `POST https://api.x.com/2/tweets`：

```json
{
  "text": "发布正文",
  "media": {
    "media_ids": ["<media_id>"]
  }
}
```

6. 保存返回的 Post ID，并生成/保存公开地址。失败重试前，先根据当前任务是否已有 Post ID 判断是否已经发布。

X 官方推荐图片、GIF、视频统一采用分块上传；一个 Post 最多附 4 张图片、1 个 GIF 或 1 个视频。具体媒体约束与账号产品级能力需在上传前动态校验。参见 [Chunked Media Upload](https://docs.x.com/x-api/media/quickstart/media-upload-chunked)、[Media Introduction](https://docs.x.com/x-api/media/introduction)、[Media Best Practices](https://docs.x.com/x-api/media/quickstart/best-practices) 和 [Create Post](https://docs.x.com/x-api/posts/create-post)。

### 3.4 需要你准备的信息

- X Developer 账号及已批准的 Project/App。
- App 名称、App ID（如控制台显示）、Client ID、Client Secret。
- 开发和生产的精确 Redirect URI。
- Website、隐私政策、服务条款 URL。
- 已开通的 API 访问/计费状态。
- 要发布到的 X 用户 ID、`@username` 和显示名称。
- 上述 5 个 Scope 的审批/授权结果。
- OAuth 完成后产生的 Access Token、Refresh Token、到期时间；这些值通过后台管理或后端 OAuth 流写入，不要填入此文件。
- 默认发布正文规则，以及视频超过 X 当前限制时是拒绝、压缩还是截断。

## 4. Instagram 接入

### 4.1 先选择一种登录路线

| 项目 | Instagram Login（推荐） | Facebook Login |
| --- | --- | --- |
| Instagram 账号 | Business 或 Creator | Business 或 Creator |
| 是否必须绑定 Facebook Page | 否 | 是 |
| API Host | `graph.instagram.com` | `graph.facebook.com` |
| 发布 Token | Instagram User Access Token | Facebook Page Access Token |
| 发布 Scope | `instagram_business_basic`、`instagram_business_content_publish` | `pages_show_list`、`instagram_basic`、`instagram_content_publish`、`pages_read_engagement` |
| 适用场景 | 只管理 Instagram，接入链路更直接 | 已围绕 Facebook Page 统一管理 Meta 资产 |

Meta 官方说明旧的 Instagram Login Scope `business_basic`、`business_content_publish` 等已于 2025-01-27 废弃，应使用带 `instagram_` 前缀的新 Scope。Instagram Login 不能访问广告或 Tagging。详见 [Meta 官方 Instagram API 集合](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-ab559ffb-8e2c-4b0a-b43a-5737b6d2f672) 和 [Facebook Login 路线说明](https://www.postman.com/meta/instagram/folder/u4g5a2a/instagram-api-with-facebook-login)。

### 4.2 推荐路线：Instagram Login

1. 将目标 Instagram 账号转换为 Business 或 Creator 专业账号。
2. 在 [Meta for Developers](https://developers.facebook.com/apps/) 创建 App，建议选择 Business 类型/业务用例。
3. 添加 Instagram 产品，选择 **Instagram API with Instagram Login / Business Login for Instagram**。
4. 配置 App Domains、Valid OAuth Redirect URI、Deauthorize Callback、Data Deletion URL、隐私政策和服务条款。
5. 在开发模式中加入 Instagram 测试账号/应用角色，并在目标 Instagram 账号侧接受邀请。
6. 使用控制台生成的 Business Login URL 发起授权，仅请求：
   - `instagram_business_basic`
   - `instagram_business_content_publish`
7. 回调中验证 `state`，按控制台和官方 Business Login 文档交换 Instagram User Access Token。
8. 保存 Instagram 专业账号 ID（`ig_user_id`）、用户名、Token、Scope 和有效期。
9. 仅服务你自己管理且已加入 App Dashboard 的账号时可先使用 Standard Access；服务其他客户的专业账号时申请 Advanced Access，并完成控制台要求的审核。

### 4.3 备选路线：Facebook Login

1. 目标 Instagram 必须是专业账号，并连接一个 Facebook Page。
2. 授权用户必须能管理该 Page。
3. Meta App 中配置 Facebook Login for Business，并请求 `pages_show_list`、`instagram_basic`、`instagram_content_publish`、`pages_read_engagement`。
4. 取得 Facebook User Access Token 后调用：

```text
GET https://graph.facebook.com/{api_version}/me/accounts
    ?fields=name,access_token,tasks,instagram_business_account
```

5. 从结果保存 Page ID、Page Access Token，以及 `instagram_business_account.id` 作为 `ig_user_id`。
6. 后续 Instagram 发布请求使用 `graph.facebook.com`、Page Access Token 和该 `ig_user_id`。

Meta 官方示例见 [Instagram Token 与 Page/IG ID 获取流程](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-af579d08-121e-4897-8f45-5fd41ace49df)。

### 4.4 Reel/视频发布调用顺序

以推荐的 Instagram Login 路线为例：

1. 将视频上传到 Meta 能匿名访问的 HTTPS URL。URL 在 Meta 拉取期间必须有效，并返回正确的 `Content-Type`、`Content-Length`，支持稳定下载。
2. 创建媒体容器：

```text
POST https://graph.instagram.com/{api_version}/{ig_user_id}/media
Authorization: Bearer <instagram_user_access_token>

media_type=REELS
video_url=https://cdn.example.com/path/video.mp4
caption=发布文案
```

3. 保存返回的 Container ID。
4. 查询 `/{container_id}?fields=status_code,status`，等待 `FINISHED`；`ERROR` 视为失败，`EXPIRED` 需要重建容器。官方建议不要高频轮询。
5. 发布容器：

```text
POST https://graph.instagram.com/{api_version}/{ig_user_id}/media_publish
Authorization: Bearer <instagram_user_access_token>

creation_id=<container_id>
```

6. 保存返回的 Instagram Media ID；如业务需要，再查询 permalink 并写回任务。
7. 发布前调用 `/content_publishing_limit` 或在本地计数。官方集合当前说明每个 Instagram 专业账号在滚动 24 小时内最多 100 个 API 发布帖，Carousel 计为一个。

Meta 当前发布指南支持单图、视频、Reel、Story 和 Carousel，但格式和账号类型有差异；例如 Facebook Login 路线下 Stories 仅适用于 Business 账号。发布媒体必须在公网服务器上。参见 [Instagram Publish Content 官方集合](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-ab559ffb-8e2c-4b0a-b43a-5737b6d2f672) 和 [Reels Publishing 示例](https://www.postman.com/meta/workspace/instagram/documentation/23987686-9386f468-7714-490f-9bfc-9442db5c8f00)。

### 4.5 媒体注意事项

- 官方 Reels 示例列出的主要约束包括 MOV/MP4、AAC 音频、H.264/HEVC 视频、23–60 FPS、建议 9:16、横向像素不超过 1920、3 秒至 15 分钟、最大 1 GB；应在实际启用的 API 版本文档中再次确认。
- 通用“封面文件”不要直接照搬到 Instagram 请求。应按当前 `/media` 端点明确支持的 `cover_url` 或缩略图时间参数实现，并以选定登录路线/API 版本的端点参考为准；若控制台文档未列出，就让平台自动选帧。
- 如果采用公网 URL 拉取，不能在 Meta 拉取完成前撤销签名 URL 或删除源文件。

### 4.6 需要你准备的信息

- 选择的登录路线：`instagram_login` 或 `facebook_login`。
- Meta Business App ID、App Secret、当前固定 Graph API Version。
- Redirect URI、App Domain、隐私政策、服务条款、Deauthorize Callback、Data Deletion URL。
- Instagram 专业账号类型、`ig_user_id`、`@username`、显示名称。
- 若选 Facebook Login：关联的 Page ID、Page 名称及管理员/任务权限。
- Access Level：Standard 或 Advanced；App 当前是 Development 还是 Live。
- 实际授权 Scope、Token 类型、Access Token、有效期。
- 可供 Meta 匿名拉取的媒体基础 URL，以及 URL 有效时长。
- 默认 `media_type`、`share_to_feed`、Caption 规则及超限处理策略。
- 审核录屏、测试账号和审核说明。

## 5. YouTube 接入

### 5.1 Google Cloud 配置

1. 在 [Google Cloud Console](https://console.cloud.google.com/) 创建独立 Project；建议开发与生产分项目。
2. 在 API Library 启用 **YouTube Data API v3**。
3. 配置 OAuth Consent Screen / Google Auth Platform：
   - Internal 或 External 用户类型；
   - App 名称、Logo、User Support Email、Developer Contact；
   - Homepage、Privacy Policy、Terms of Service；
   - Authorized Domains；
   - Scope；
   - 测试阶段的 Test Users。
4. 创建 **OAuth Client ID → Web application**，登记开发和生产 Redirect URI，下载/记录 Client ID 与 Client Secret。
5. 上传功能最小 Scope 使用 `https://www.googleapis.com/auth/youtube.upload`。若页面还要读取频道详情或列出频道资源，再单独评估 `youtube.readonly`，不要为了方便直接申请更宽权限。

Google 官方接入总览见 [YouTube Data API Overview](https://developers.google.com/youtube/v3/getting-started)，OAuth 应用资料和审核要求见 [Submitting your app for verification](https://support.google.com/cloud/answer/13461325) 与 [Verification requirements](https://support.google.com/cloud/answer/13464321)。

### 5.2 OAuth 流程

1. 后端生成并保存一次性 `state`。
2. 重定向到 `https://accounts.google.com/o/oauth2/v2/auth`，至少携带：
   - `client_id`
   - `redirect_uri`
   - `response_type=code`
   - `scope=https://www.googleapis.com/auth/youtube.upload`
   - `access_type=offline`
   - `include_granted_scopes=true`
   - `state`
3. 首次连接或确实需要重新取得 Refresh Token 时使用 `prompt=consent`；不要在每次登录时强制重复同意。
4. 回调验证 `state`，将授权码提交给 `https://oauth2.googleapis.com/token`。
5. 加密保存 Access Token、Refresh Token、到期时间和 Scope。Google 不保证每次重新授权都返回新的 Refresh Token，因此刷新 Access Token 时不能用空值覆盖数据库里已有的 Refresh Token。
6. 保存用户明确选择并授权的 Channel ID、Channel Title；不要只凭 Google 邮箱推断频道。

详细服务端流程、offline access 和刷新请求见 [Using OAuth 2.0 for Web Server Applications](https://developers.google.com/youtube/v3/guides/auth/server-side-web-apps)。

### 5.3 视频与封面发布调用顺序

1. 组织 `video` 资源：
   - `snippet.title`
   - `snippet.description`
   - `snippet.tags`
   - `snippet.categoryId`
   - `status.privacyStatus`：`private`、`unlisted` 或 `public`
   - `status.selfDeclaredMadeForKids`
   - `status.containsSyntheticMedia`：真实感 AI/合成内容按实际情况披露
   - 如定时发布，设置合规的 `status.publishAt`，并遵守该字段要求的隐私状态。
2. 启动 Resumable Upload：

```text
POST https://www.googleapis.com/upload/youtube/v3/videos
     ?uploadType=resumable&part=snippet,status
Authorization: Bearer <access_token>
```

3. 保存响应 `Location` 上传会话 URL，按官方协议 `PUT` 视频；网络中断时查询偏移并续传，不要从头创建另一个视频。
4. 成功后保存 YouTube Video ID。
5. 使用 `videos.list(part=processingDetails,id=<video_id>)` 查询 `processingDetails.processingStatus`，直到 `succeeded` 或 `failed`。
6. 如用户提供自定义封面，在拿到 Video ID 后调用：

```text
POST https://www.googleapis.com/upload/youtube/v3/thumbnails/set?videoId=<video_id>
```

   官方当前接受 JPEG/PNG/`application/octet-stream`，最大 2 MB；频道还必须具备设置自定义缩略图的资格。
7. 只有上传、处理和必要的封面设置全部达到预期状态，项目发布任务才标记为成功。

参见 [videos.insert](https://developers.google.com/youtube/v3/docs/videos/insert)、[Resumable Uploads](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol)、[处理状态](https://developers.google.com/youtube/v3/guides/implementation/videos)、[Video 资源字段](https://developers.google.com/youtube/v3/docs/videos) 和 [thumbnails.set](https://developers.google.com/youtube/v3/docs/thumbnails/set)。

### 5.4 审核与配额注意事项

## 6. Facebook 接入

### 6.1 账号与 App 前置条件

1. 创建或选定 Facebook Page；真实发布目标是 Page，不是个人 Profile。
2. 确认用于授权的 Facebook 用户对该 Page 拥有创建内容所需的 Page Task/权限。
3. 在 [Meta for Developers](https://developers.facebook.com/apps/) 创建 Business App，添加 Facebook Login for Business 和 Page/Video 发布所需用例。
4. 配置 App Domains、Valid OAuth Redirect URI、隐私政策、服务条款、Data Deletion URL 和 Deauthorize Callback。
5. 开发模式只用 App Role/Test User 和自有 Page 验证；为其他客户的 Page 发布前，申请所需权限的 Advanced Access/App Review，并完成控制台要求的 Business Verification。
6. 固定一个仍受支持的 Graph API Version，保存到项目的平台配置中。

### 6.2 OAuth、权限和 Page Token

最小权限建议：

| Permission | 用途 |
| --- | --- |
| `pages_show_list` | 列出授权用户可管理的 Page |
| `pages_read_engagement` | 读取 Page 基础数据和发布状态所需信息 |
| `pages_manage_posts` | 代表 Page 创建、编辑、删除内容 |

流程：

1. 发起 Facebook Login，使用 Authorization Code 流并校验 `state`。
2. 后端交换 Facebook User Access Token，并记录授权 Permission 与到期时间。
3. 调用以下接口取得用户能管理的 Page 和 Page Access Token：

```text
GET https://graph.facebook.com/{api_version}/me/accounts
    ?fields=name,access_token,tasks
    &access_token=<user_access_token>
```

4. 让用户明确选择 Page；保存 Page ID、Page Name、Page Access Token、`tasks` 和 Token 有效期。
5. 定期使用官方 Token 调试/检查机制验证 Token 类型、App、用户、Scope 和到期时间。不要假设 Page Token 永不过期。

Meta 官方 Page Token 示例见 [Facebook API 官方 Postman 集合](https://www.postman.com/meta/facebook/documentation/r56bjfd/facebook-api?entity=request-23987686-0b79260c-96bd-49de-875b-6076213785fc)。

### 6.3 Page Reel 发布调用顺序

1. 初始化 Reel：

```text
POST https://graph.facebook.com/{api_version}/me/video_reels
     ?upload_phase=start
Authorization: Bearer <page_access_token>
```

2. 保存返回的 `video_id` 和 `upload_url`。
3. 上传视频，二选一：
   - 本地文件：向返回的 `rupload.facebook.com` URL 发送二进制，带 `Authorization: OAuth <page_access_token>`、`offset: 0`、`file_size`。
   - 公网文件：向同一上传 URL 发送 `file_url` Header，让 Meta 从 CDN 拉取。
4. 可用 `GET /{video_id}?fields=status` 查询上传、处理和发布阶段。
5. 完成并发布：

```text
POST https://graph.facebook.com/{api_version}/me/video_reels
     ?upload_phase=finish
     &video_id=<video_id>
     &video_state=PUBLISHED
     &description=<description>
     &title=<title>
Authorization: Bearer <page_access_token>
```

6. 继续查询 `status`，直到处理/发布成功；保存 `video_id` 和最终 Page Reel URL。
7. 如业务还需要普通 Page Video、Feed 图文或排期发布，应分别实现其官方端点和参数，不能把 Reel 请求参数直接复用过去。

Meta 官方集合当前给出的 Page Reel 基线为竖屏 9:16、最低 540×960、最低 23 FPS、4–60 秒，并列出所支持的视频容器。平台可能调整限制，应在启用的 Graph API Version 下再次确认。完整示例见 [Facebook Reels Publishing 官方集合](https://www.postman.com/meta/facebook/documentation/r56bjfd/facebook-api?entity=request-23987686-0b79260c-96bd-49de-875b-6076213785fc)。

### 6.4 需要你准备的信息

- Meta Business App ID、App Secret、固定 Graph API Version。
- Facebook Business Portfolio ID（如使用）及 Business Verification 状态。
- Redirect URI、App Domain、主页、隐私政策、服务条款、Data Deletion URL、Deauthorize Callback。
- Facebook Page ID、Page Name、Page URL。
- 授权用户对 Page 的实际 `tasks`/权限。
- `pages_show_list`、`pages_read_engagement`、`pages_manage_posts` 的 Access Level 和审核状态。
- Facebook User Access Token、Page Access Token、Token 到期时间；通过 OAuth/后台安全写入。
- 默认发布类型：Page Reel、普通 Page Video 或 Feed Post；若多种都要支持，应分别给出产品规则。
- 默认标题、Description、发布状态（Draft/Scheduled/Published）、排期时区。
- 视频不符合 Reel 比例/时长时的拒绝、转码或改发普通视频策略。
- App Review 录屏、测试 Page、测试用户和审核步骤。

## 7. 与本项目现有配置字段的对应关系

项目已经预置四个平台模板，但默认禁用；平台与账号数据分存在 `publish_platforms` 和 `publish_accounts`。

### 7.1 `publish_platforms`

| 平台 | `code` | `adapter_type` | `api_base_url` | `auth_type` |
| --- | --- | --- | --- | --- |
| X | `x` | `x_v2` | `https://api.x.com` | `oauth2_pkce` |
| Instagram Login | `instagram` | `instagram_graph` | `https://graph.instagram.com` | `oauth2` |
| YouTube | `youtube` | `youtube_data_api_v3` | `https://www.googleapis.com/youtube/v3` | `oauth2` |
| Facebook | `facebook` | `facebook_graph` | `https://graph.facebook.com` | `oauth2` |

配置建议：

- `api_version`：Meta 固定 Graph 版本；X/YouTube 可按 Adapter 约定保留或填写逻辑版本。
- `capabilities`：只描述已实现并验证的能力，不能因平台理论支持就提前显示可用。
- `extra_config`：保存非 Secret 的平台参数，例如 OAuth URL、Token URL、默认 chunk size、轮询间隔、默认发布类型。
- `enabled`：只有完成凭证配置、真实测试和回滚验证后再启用。

## 9. 接入实施与验收顺序

建议一次只打通一个平台，避免 OAuth、上传和异步处理问题互相干扰：

1. 建立正式 HTTPS 域名、四个平台回调路径和 Instagram 公网媒体存储。
2. 创建开发/测试 App，先加入自有测试账号，不立即申请生产审核。
3. 实现 OAuth，验证账号 ID、Scope、Token 刷新、撤销和重新授权。
4. 先发布最短合规测试视频：YouTube 使用 Private，Facebook 可先 Draft，X/Instagram 使用专用测试账号。
5. 验证大文件分块/续传、处理状态轮询、超时恢复和重复任务幂等。
6. 分别验证标题、正文、标签、隐私、AI 内容披露、排期和封面；平台不支持的字段必须明确忽略或拒绝，不能静默误导用户。
7. 检查日志和 API 响应是否完全脱敏，确认普通用户无法看到 Client Secret/Token。
8. 准备审核录屏和权限说明，提交 Advanced Access/OAuth Verification/YouTube Audit。
9. 审核通过后切换 Production App/凭证，再逐个平台启用 `publish_platforms.enabled`。
10. 生产首发保持低频，监控 API 错误、Token 到期、平台限流、处理失败和配额。
